Zero-Trust Database Access: SSH Tunnels, Topology, and the Agent

Databases sit behind the last door worth defending. The common ways in — a public 3306 port, a static password pasted into a tool, an agent holding the .my.cnf — are each a single mistake away from a breach. The safer path is boring and mechanical: reach the database through SSH, pin the host identity, grant per request, and keep the password out of the agent's reach.

The database is the last door

Networks can be segmented, web servers can be ephemeral, but the database usually holds the crown jewels and stays put. That makes it the favorite target — and it makes the access pattern around it the thing to get right.

The three most common patterns are all wrong:

  • Expose MySQL on a public port. A standing 3306 listener is a daily brute-force target, even with a strong password. There is no reason for the database to speak to the public internet at all.
  • Share one static password. One credential reused across humans, cron jobs, and agents means one leak revokes nothing and implicates everyone. There is no per-action boundary.
  • Hand the agent the connection string. The password then lives in chat history, model context, and tool logs, and a single prompt injection turns read access into exfiltration. The database password is the one secret that should never become model input.

Zero-trust database access means: no standing open port, no shared static credential, and every request authenticated, authorized, and scoped to the minimum privilege.

The boring pattern that works: SSH in, then reach the database

The robust pattern predates AI and still holds:

  1. Reach the host over SSH — direct, or through a jump host. The database port is never exposed; mysql connects over the SSH transport or a tunnel.
  2. Pin the host identity. Verify the SSH host key against a trusted record (known_hosts or a pinned fingerprint). Identity verification must fail closed: an unknown or changed key stops the operation.
  3. Use short-lived, scoped credentials. A credential that expires per request, or a grant that covers one action family for a few minutes and can be revoked, beats a permanent password.
  4. Authorize each action. Reading row counts is not the same as DROP TABLE. The person who owns the machine approves the exact operation, not "the agent has DB access".
  5. Keep the password out of the agent's channel. The credential is injected by the transport layer, never composed into the command line, environment, or returned output.

None of this is exotic. It is how production SSH access has worked for two decades; the difference today is that we now automate it for agents without collapsing the trust boundary.

Topology: replace IP guessing with computed answers

An agent that asks "can the crawler reach MySQL?" should not be reading a network diagram or guessing from a spreadsheet of IPs. It should ask a system that stores typed, directed relationships between registered resources and computes the answer from observations.

SAFA models resources (hosts, databases, services) and their relationships, then exposes a small, task-specific projection to the agent:

  • Placement — topology show: what lives in the same site or domain as this resource? (e.g. a NAS co-located with a virtualization host, a router, and a database host).
  • Reachability — topology path FROM TO: is there a verified, directed path from A to B? The answer is confirmed, not-found, or indeterminate — never a guess. A not-found answer does not authorize a direct connection attempt.
  • Impact — topology impact ALIAS: what is affected if this resource goes down? A computed affected set, with supporting edges.
Why this matters for agents: an agent cannot safely "figure out" the route. It can only act on a Broker-computed answer with an explicit outcome. Desired/asserted relationships and observed facts are kept distinct — SAFA does not let a diagram edge masquerade as verified connectivity.

What the agent actually experiences

In the real recorded session, the agent never saw an IP, username, or key. It asked questions like:

# Is there a verified path from the NAS to the database host?
safa topology path nas.primary data.home --limit 64
# → outcome: not-found   (no invented route, no fallback connection)

# What is co-located with the NAS?
safa topology show nas.primary --limit 64
# → placement: site.home, with router, virtualization host,
#   database host, workstation

# Bounded read-only diagnostics on the database host's machine
safa exec data.home --intent "Check root filesystem capacity" -- df -h /

Notice what is absent: no 3306, no mysql -u root -p..., no connection string. The database host itself (a real registered resource) can be inspected read-only, and the topology surface answers reachability questions without handing over a route.

Database operations today and next

SAFA's current preview is deliberately narrow: SSH hosts are the executable profile, with allow-listed read-only diagnostics. Databases, object stores, caches, and HTTP services can be registered as typed records — the resource directory is generic, not transport-specific — but their protocol operations are gated pending review. Nothing in the design leaks a database password to the agent, because the same rules apply: the credential lives in the Broker boundary, the agent holds an alias and an intent, and high-privilege actions require macOS user-presence approval.

The route from here is additive: typed database records already exist, the authorization model already exists (Touch ID approval for protected actions is current behavior), and the transport pattern is SSH itself. The remaining work is reviewed adapter operations — exactly the kind of capability that should ship with conformance fixtures, not promises.

FAQ

How do I access MySQL through SSH securely?

Do not expose MySQL on a public port. Connect through an SSH tunnel or jump host, pin the host identity, use short-lived or per-request credentials, and authorize each action. Never pass the database password to an AI agent.

What is zero-trust database access?

Assume no network location is trusted by default: every request is authenticated, authorized per action, and scoped to minimum privilege. No standing open port, no shared static credentials, no credential reuse across tools.

Can an AI agent query my database without the password?

The safe pattern keeps the credential in a native local boundary and gives the agent a bounded, approved operation against a logical resource. SAFA currently registers database records and gates their operations; SSH read-only diagnostics are available now.

Why is topology important for infrastructure access?

IPs are guessable and rot; topology answers are computed from verified observations. An agent asking "can the crawler reach MySQL?" gets a confirmed/not-found answer instead of inventing a route.
